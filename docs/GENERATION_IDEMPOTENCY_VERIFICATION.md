# Durable asynchronous generation idempotency — implementation handoff

## Implemented contract

Optional `Idempotency-Key` now reserves an encrypted durable minimal ledger entry before reference resolution, outstanding-job reservation, task creation or upstream execution. Supported JSON routes: `/v1/images/tasks`, `/v1/images/generations` with `async:true` (canonical image operation), `/v1/videos` and `/v1/videos/generations` (canonical video operation). Sync image, all edits (including async multipart), chat and responses reject the header with 400. Requests without a header retain their existing contract.

The ledger binds owner + canonical operation + key digest to a canonical validated request digest including authority key version, and allocates the task ID durably before any downstream work. Model aliases normalize through resolve_model; async image route flags do not change the binding. Reference fields bind before fetching; they are never persisted in the ledger. Only encrypted scope/request digests, opaque task ID and timestamps are stored, using the existing externally provisioned AccountCipher key. Encryption is whole-file Fernet; no plaintext prompts, key values, capability references or owner labels in the ledger. Existing task records still persist prompts as documented in SECURITY.md; this change does not encrypt tasks/media.

Same-key requests return the same ID across concurrent admission, process reconstruction and task deletion. Payload/authority conflict is 409. A crash/failed reference/task write/thread start after reservation consumes the key permanently; no retry launches a second job. Missing task returns status `unknown`, never permission to submit again. Completed records use the existing authorized task response path for fresh protected-media results. General authenticated request budget remains charged on every request; storage and heavy generation admission run only for the first keyed admission. Revoked credentials are rejected before replay. No in-process waiting on a duplicate key is required.

Ledger bounds are conservative: 10,000 entries, 24-hour replay window. Expiry produces 409 but **does not evict or reuse a key**; full capacity produces 503 for new keys while retained valid replays remain available. This intentionally trades availability for no-double-submit safety. There is no automatic ledger cleanup; offline operator reconciliation is required before capacity reclamation. Do not delete the ledger, restore an older ledger than task state, rotate its encryption key implicitly or run multiple runtimes. The incumbent single-runtime lock/storage restriction remains. No production migration, key provision, cleanup or deployment was performed.

Keyed workers disable both automatic account-rotation generation retries and engine resend/Enter fallback after uncertain clicks or delivery. This is at-most-one local generation invocation/send attempt, not an upstream exactly-once guarantee: Muse has no verified upstream idempotency contract, and no live Muse calls were made.

No automatic POST retry added; existing polling remains GET-only. Browser reload loses RAM keys; check task history before a new intent. Dashboard markup/functions otherwise untouched.

## Backend acceptance follow-up (offline, not independent acceptance)

Backend edits: persistent `admin-authority.json` epoch plus initialized marker; real admin rotation commits epoch before updating `.env`/CFG. Authentication reads fresh epoch; outstanding jobs capture/check it, including stale captured principals. Old credentials return 401; same generation key under new epoch conflicts 409. A stale rotation principal is rejected under the rotation lock. Mismatched restart key fails closed rather than adopting a stale environment key. Rotation persistence failure may leave the service unavailable and requires offline reconciliation; it never silently restores old authority.

Ledger bootstrap is now **explicit**, not automatic. Default startup with missing ledger fails. `MUSE2API_LEDGER_INITIALIZE=1` permits first empty initialization only when neither ledger nor `.initialized` marker exists. Marker is fsynced first; interrupted bootstrap and removal of either file require offline reconciliation. Remove the initialization flag after first approved initialization. The offline runner sets it only for its disposable synthetic HOME. This flag is NOT authorization to reset a previously used deployment. If both artifacts are deleted/rolled back together, local markers cannot establish historical completeness: restore a verified matching backup; never infer safety from absence.

New encrypted entries include an owner digest. Default `MUSE2API_LEDGER_PER_OWNER=1000`, validated 1..10000, counts all operations and retained/expired keys for that owner. Global hard maximum remains 10000; replays are checked before either limit. No eviction, expiration deletion, or automatic quota reset. One tenant cannot consume the default global capacity; enough tenants can still reach the global safe cap. Capacity/write failures return 503 before references/tasks.

**Offline initialization/migration/reconciliation policy:** stop all runtimes and preserve a consistent restricted backup of ledger, markers, authority state, encryption key and task state. For a provably never-used synthetic/fresh deployment, explicitly initialize once. Existing old-schema ledgers (without owner digests) are rejected: scope digests do not reveal owners, so automatic migration cannot safely assign fair accounting. Do not discard them. Reconstruct owner associations only from independently verified admission records in an offline reviewed migration, preserving every scope/binding/ID/timestamp; otherwise remain unavailable. Reclamation requires deliberate offline proof that removed bindings can never be submitted again (or a permanent external tombstone system); TTL/task deletion alone is not proof. No migration/reclamation utility or production operation was executed here.

Orphan queued/processing image/video receipts and GET observations report `unknown`/uncertain when no outstanding runtime job exists. Startup interruption records unknown with “Do not resubmit”, not failed/retry instructions. Worker liveness is reservation-based, not a distributed health guarantee. No resubmission mechanism added.
